# Loop Algorithm Quality Tuning — Implementation Plan

## Overview

Implement paved-surface preference in route selection, expose surface quality in
the API response and UI, tune waypoint geometry, and lock measurable acceptance
criteria with automated regression tests. Satisfies PRD Business Logic
(deprioritise unpaved segments) and the S-03 roadmap north star.

## Current State Analysis

- `LoopRouteGenerator` generates 3 parallel ORS candidates at bearings
  `[base+60°, base+180°, base+300°]`; radius = `targetMidMeters / 2.0 * 0.45`.
- Route selection: primary = distance in range + overlap ≤ 10%, ordered by
  distance-to-midpoint. Fallback relaxes overlap to 40%.
- ORS already returns `surface` + `waytype` extra info; `OrsMapper.BuildSegments()`
  maps them to `RouteWaySegment[]` on every result.
- **Gap**: surface data is collected but never used for selection or scoring.
  Paved-surface preference from the PRD is unimplemented.
- No shape-quality or paved-fraction criteria exist; no regression tests for
  route quality beyond distance bounds and overlap.

## Desired End State

A generated route:
- Is selected preferring the candidate with the highest paved-segment fraction.
- Exposes `pavedRatio` in the JSON response and in the RouteInfoPanel ("X% paved").
- Is generated by a geometry algorithm whose `RadiusFactor` and bearing count are
  named constants, calibrated against real ORS runs for Polish test cities.
- Satisfies measurable quality thresholds verified by automated integration tests.

### Acceptance Thresholds

These are locked after the Phase 4 calibration run. Proposed values:

| Metric | Primary threshold | Fallback / warning |
|---|---|---|
| `pavedRatio` | ≥ 0.95 (primary) | ≥ 0.80 (rural fallback) |
| Distance accuracy | `|selected − midpoint| / midpoint ≤ 0.15` | — |
| Bbox aspect ratio | ≤ 3.0 (hard fail in tests) | — |
| Overlap ratio | ≤ 0.10 (existing PRD) | ≤ 0.40 (existing fallback) |

Fake ORS integration tests validate the **logic** (selection prefers most-paved,
respects constraints). Live ORS smoke tests (manually run, skipped in CI) validate
that real ORS actually produces routes meeting these thresholds for the test cities.

### Key Discoveries

- `RouteWaySegment.FromIndex`/`ToIndex` index into `RouteGeometry.Coordinates`
  — segment lengths computable from coordinate deltas without extra ORS calls.
  (`src/backend/VeloRoute/Routing/RouteResult.cs`)
- Existing `OrsMapper.BuildSegments()` produces contiguous, non-overlapping
  segments covering the full coordinate array.
  (`src/backend/VeloRoute/Routing/OrsMapper.cs:11`)
- `OverlapDetector` pattern (static class, pure function, NTS) is the template
  for `PavedRatioCalculator`. (`src/backend/VeloRoute/Routing/OverlapDetector.cs`)
- `RouteResult` is a C# record — a computed property body (not a constructor
  parameter) exposes `PavedRatio` without breaking existing call sites or tests.
  (`src/backend/VeloRoute/Routing/RouteResult.cs`)
- `FakeOpenRouteServiceClient.Results` is a `ConcurrentQueue` — quality tests
  inject routes with controlled segment data using the existing pattern.
  (`src/backend/VeloRoute.Tests/Routing/TestInfrastructure.cs:14`)
- The `MakeRoute` helper in `LoopRouteIntegrationTests` passes `[]` for
  segments; after adding `PavedRatio` as a computed property (not a constructor
  field), those existing tests continue to compile without changes.
- Radius `0.45` is an inline literal at `LoopRouteGenerator.cs:27`; bearing
  offsets `60°/180°/300°` are inline at lines 31–35.
- Program.cs returns `Results.Ok(result.Value)` — `PavedRatio` on `RouteResult`
  serialises automatically via System.Text.Json.
  (`src/backend/VeloRoute/Program.cs`)

## What We're NOT Doing

- Configurable paved-threshold per user request (v2).
- Hard-excluding routes below a paved floor (degrades rural coverage; scoring
  is sufficient).
- Traffic-volume data (PRD: "optionally" — deferred).
- Convex-hull compactness score in production code (test-only bbox check).
- Full road-type breakdown + warnings in UI (deferred to separate slice).
- Multiple route proposals (v2).

## Implementation Approach

Four sequential phases, each independently verifiable:

1. **Compute + expose paved ratio** — add `PavedRatioCalculator`, computed
   property on `RouteResult`, frontend type + UI line.
2. **Use paved ratio in selection** — add as primary sort key in
   `LoopRouteGenerator` (pavedRatio desc, then distance-to-midpoint).
3. **Geometry tuning** — extract `RadiusFactor` / bearing count as named
   constants; calibrate values against live ORS runs; bake optimal values in.
4. **Quality acceptance tests** — lock thresholds in fake-ORS integration tests;
   add live ORS smoke tests (skipped in CI).

## Phase 1: Paved Ratio Computation and Exposure

### Overview

Add `PavedRatioCalculator`, surface it as a computed property on `RouteResult`,
propagate through the API response, update the TypeScript type, and display it
in `RouteInfoPanel`.

### Changes Required

#### 1. PavedRatioCalculator

**File**: `src/backend/VeloRoute/Routing/PavedRatioCalculator.cs`

**Intent**: New static helper that computes the fraction of a route's length covered
by road-bikeable paved surfaces. Mirrors the `OverlapDetector` pattern.

**Contract**: `internal static double Compute(RouteResult route)` → value in [0.0, 1.0].
Returns 0.0 if `route.Segments` is empty (no surface data from ORS).

Paved surfaces: `SurfaceType.Paved`, `Asphalt`, `Concrete`, `Cobblestone`,
`Metal`, `PavingStones`.

Segment length uses coordinate-delta Euclidean distance (same degree-space
approximation used by `OverlapDetector`). Since this is a ratio, unit cancellation
means the approximation is exact.

Total paved length / total route length across all segments. If total is zero,
return 0.0.

#### 2. PavedRatio on RouteResult

**File**: `src/backend/VeloRoute/Routing/RouteResult.cs`

**Intent**: Expose paved ratio as a public property so it serialises in the JSON
response and is usable in `LoopRouteGenerator` selection.

**Contract**: Add a computed property body to the `RouteResult` record:
`public double PavedRatio => PavedRatioCalculator.Compute(this);`
No constructor-signature change — existing `new RouteResult(geometry, distance, segments)`
call sites are unaffected.

#### 3. TypeScript type update

**File**: `src/frontend/src/types/route.ts`

**Intent**: Reflect the new API field in the frontend type contract.

**Contract**: Add `pavedRatio: number` to the `RouteResult` interface (after `segments`).

#### 4. RouteInfoPanel surface line

**File**: `src/frontend/src/components/RouteInfoPanel.tsx`

**Intent**: Show the user what surface quality the generated route has, satisfying
the PRD Business Logic ("short route summary listing road types used").

**Contract**: Below the "Total distance" block, add a "Surface quality" line
displaying `Math.round(route.pavedRatio * 100)` followed by "% paved". Use the
same `text-sm text-zinc-500` / `text-sm font-medium text-zinc-900` two-line
pattern already used for distance. When `pavedRatio === 0` (no segment data),
show "Unknown" instead of "0% paved".

### Success Criteria

#### Automated Verification

- `dotnet build src/backend/VeloRoute.sln` — no warnings or errors
- `dotnet test src/backend/VeloRoute.sln` — all existing tests still pass
- `npm run build --prefix src/frontend` — no TypeScript errors

#### Manual Verification

- `POST /routes/loop` response JSON includes `"pavedRatio": <number>` field
- RouteInfoPanel shows "X% paved" beneath the distance readout for a real route
- When fake route has empty segments, UI shows "Unknown" not "0%"

## Phase 2: Paved Ratio in Route Selection

### Overview

Update `LoopRouteGenerator` to prefer the candidate with the highest paved ratio
when multiple candidates meet the distance and overlap constraints.

### Changes Required

#### 1. Selection order update

**File**: `src/backend/VeloRoute/Routing/LoopRouteGenerator.cs`

**Intent**: Among candidates that pass distance and overlap constraints, prefer the
route with the highest paved fraction. Distance accuracy is the tiebreaker.

**Contract**: In the primary candidate projection (line 61–66), add:
`pavedRatio = route.PavedRatio`

Change the primary `.OrderBy(c => Math.Abs(c.distance - targetMidMeters))`
to:
```
.OrderByDescending(c => c.pavedRatio)
.ThenBy(c => Math.Abs(c.distance - targetMidMeters))
```

The fallback path (lines 79–83) is unchanged — it already orders by overlap
ratio; paved preference only applies to the primary path where all constraints
are met.

### Success Criteria

#### Automated Verification

- `dotnet test src/backend/VeloRoute.sln` — all tests pass

#### Manual Verification

- When two valid candidates have different paved ratios (verify via logs if
  needed), the more-paved route is returned

## Phase 3: Geometry Tuning

### Overview

Extract the inline `0.45` radius factor and the hardcoded bearing offsets as
named constants. Optionally increase bearing count from 3 to 4. Calibrate
values against live ORS runs for the test cities and bake optimal values in.

### Changes Required

#### 1. Extract named constants

**File**: `src/backend/VeloRoute/Routing/LoopRouteGenerator.cs`

**Intent**: Make the geometry parameters discoverable and tuneable without hunting
for inline literals.

**Contract**: At the class level, add:
```csharp
private const double RadiusFactor = 0.45;
private const int BearingCount = 3;  // increase to 4 after calibration if beneficial
```

Replace the inline `0.45` on line 27 with `RadiusFactor`. Replace the hardcoded
`[60, 180, 300]` bearing array with a computed array using:

```csharp
double phaseOffset = 360.0 / (BearingCount * 2);
double[] bearings = Enumerable.Range(0, BearingCount)
    .Select(i => (baseBearing + phaseOffset + 360.0 / BearingCount * i) % 360)
    .ToArray();
```

For `BearingCount = 3` this reproduces the current `[base+60, base+180, base+300]`
exactly. For `BearingCount = 4` it produces `[base+45, base+135, base+225, base+315]`,
which adds one more ORS call but gives better geographic coverage.

Note: increasing `BearingCount` adds one task to `Task.WhenAll`. The 4.5-second
timeout in `Program.cs` already governs wall time; no timeout change needed.

#### 2. Calibration run

After implementing the constants, run the live ORS smoke tests (added in Phase 4)
for Warsaw outskirts, Mazury, and Gdynia with `RadiusFactor` values `{0.35, 0.40,
0.45, 0.50}` and `BearingCount` values `{3, 4}`. Pick the combination that
maximises average pavedRatio while keeping distance accuracy ≤ 0.15 and bbox
aspect ratio ≤ 3.0. Update the constants and document the winning configuration.

### Success Criteria

#### Automated Verification

- `dotnet build src/backend/VeloRoute.sln` — compiles cleanly
- `dotnet test src/backend/VeloRoute.sln` — all tests pass (3 OR 4 bearings)

#### Manual Verification

- Live ORS smoke tests run for each city with each `{RadiusFactor, BearingCount}`
  combination; results logged to a calibration table in `context/changes/loop-algorithm-tuning/calibration.md`
- Optimal constants chosen and committed; calibration table retained in the
  change folder for traceability

**Pause for manual confirmation (calibration table review) before Phase 4.**

## Phase 4: Quality Acceptance Tests

### Overview

Add a `RouteQualityTests` class asserting all four thresholds against controlled
fake-ORS scenarios. Add live ORS smoke tests (skipped in CI) for the three Polish
test cities.

### Changes Required

#### 1. RouteQualityTests

**File**: `src/backend/VeloRoute.Tests/Routing/RouteQualityTests.cs`

**Intent**: Lock the quality criteria as automated regression tests so future
changes to `LoopRouteGenerator`, `PavedRatioCalculator`, or `OverlapDetector`
can't silently degrade route quality.

**Contract**: New xUnit class in `namespace VeloRoute.Tests.Routing`. Uses
`VeloRouteWebApplicationFactory` + `FakeOpenRouteServiceClient` (existing
pattern). All tests POST to `/routes/loop` with Polish coordinates:
`{"startLon":21.05,"startLat":52.33,"minKm":20,"maxKm":30}` (Warsaw outskirts
/ Białołęka area).

Required test scenarios:

- **`SelectsMostPavedCandidateAmongEquallyValidRoutes`**: Enqueue two candidates
  both in range and under 10% overlap — one with high-paved segments (≥ 0.80),
  one with low-paved segments (≤ 0.40). Assert response route has the higher
  pavedRatio. Uses `MakeRouteWithSegments(distance, coords, segments)` helper.

- **`PavedRatioInResponseIsCorrect`**: Enqueue one valid route with controlled
  segment data. Deserialise response JSON. Assert `pavedRatio` matches expected
  value within ±0.01.

- **`DistanceAccuracyWithinFifteenPercent`**: Enqueue a valid route at exactly
  the target midpoint (25 km). Assert selected distance is within ±15% of midpoint.
  (Validates existing behaviour; serves as regression guard.)

- **`BboxAspectRatioUnderThree`**: Enqueue a valid route whose geometry is a
  roughly circular loop (e.g., square with 4 corners). Assert bbox
  `max(width, height) / min(width, height) ≤ 3.0`. Helper: compute bbox from
  coordinate list.

- **`WhenAllCandidatesUnpavedInRangePrimaryPathReturnsLeastUnpaved`**: Enqueue
  three in-range candidates with paved ratios 0.10, 0.25, 0.40. Assert returned
  route has pavedRatio ≈ 0.40 (least unpaved wins).

Add a private `MakeRouteWithSegments(double distanceMeters,
IReadOnlyList<RouteCoordinate> coords, IReadOnlyList<RouteWaySegment> segments)`
helper to the test class, mirroring the existing `MakeRoute` helper in
`LoopRouteIntegrationTests`.

Add a private `BboxAspectRatio(IReadOnlyList<RouteCoordinate> coords)` helper
that returns `max(lonSpan, latSpan) / min(lonSpan, latSpan)`.

#### 2. Live ORS smoke tests

**File**: `src/backend/VeloRoute.Tests/Routing/OrsLiveSmokeTests.cs`

**Intent**: Validate that real ORS generates routes meeting quality thresholds for
the three Polish test cities. Skipped in CI; run manually during calibration and
before releases.

**Contract**: New xUnit class with `[Fact(Skip = "Live ORS — run manually with
ORS:ApiKey set")]` on all tests. Requires real `IOpenRouteServiceClient` wired
to live ORS (reads `ORS:ApiKey` from environment / user secrets). Does NOT use
`FakeOpenRouteServiceClient`.

Three test cities, each with 20–30 km range:

| Test name | Coordinates | Geography |
|---|---|---|
| `LiveOrs_WarsawOutskirts_MeetsQualityThresholds` | 52.33°N, 21.05°E (Białołęka) | Suburban |
| `LiveOrs_Mazury_MeetsQualityThresholds` | 53.87°N, 21.57°E (Mrągowo area) | Rural / lake |
| `LiveOrs_Gdynia_MeetsQualityThresholds` | 54.52°N, 18.53°E (Gdynia) | Coastal |

Each test asserts: HTTP 200, `pavedRatio ≥ 0.90` (slightly relaxed for real ORS road snapping),
`overlapRatio ≤ 0.10`, bbox aspect ratio ≤ 3.0, distance within ±15% of midpoint.

### Success Criteria

#### Automated Verification

- `dotnet test src/backend/VeloRoute.sln` — all `RouteQualityTests` pass;
  `OrsLiveSmokeTests` skipped (not run in CI)
- `dotnet test --filter "FullyQualifiedName~RouteQualityTests"` — 5 tests pass

#### Manual Verification

- `context/changes/loop-algorithm-tuning/calibration.md` updated with final
