## Step 5 — Refactor ranking

Ranked by (core-invariant value) × (how weakly today's code enforces it):

1. **#1 — `LoopRouteGenerator.SelectBestRoute` overlap/paved fallback** (`LoopRouteGenerator.cs:90-138`). Highest value (it *is* the product's core differentiator per Step 2) and highest risk: the PRD states a hard 10% ceiling as an unmodified v1 guarantee, but the implementation silently degrades to "best available, however bad" with a warning threshold (40%) that doesn't match the documented one (10%), and a 10–40% band that produces no signal to anyone. This is the single place where documented domain rule and shipped behavior diverge most, and it is user-facing (route quality is what users evaluate the product on).
2. **#2 — Scenic/low-traffic + POI preference, entirely missing** (Step 4, rows 3–4). Equally core by product intent, but ranked below #1 because it is a known, tracked gap (`S-07` explicitly "parked" in the roadmap) rather than a silent contract violation — the team already has visibility into it. The refactor risk here is `prd-v2.md`'s Business Logic Changes section describing it in the present tense as already governing generation, which will mislead anyone reading the PRD as ground truth.
3. **#3 — Auto-name generation location** (Step 4, row 5). Lower risk: it is a UX default, not a safety/data-integrity invariant, and may simply live client-side (unverified in this pass, since frontend `my-routes`/save-flow code was out of scope here). Worth a follow-up grep of `src/frontend/src` before treating it as a real gap.

## Summary

This distillation extracted VeloRoute's ubiquitous language and domain model from `prd-v2.md`, `roadmap.md`, and the ASP.NET Core backend under `src/backend/VeloRoute/`, classifying loop-route generation and the route library as Core, sharing and GPX export as Supporting, and auth/account-deletion as Generic (delegated to Clerk). Three aggregate candidates emerged — `Route` (owned by one `User`), `Share` (1:1 with `Route`, cascade-deleted with it), and the ephemeral generation-time `RouteResult` — with ownership, share-uniqueness, and cascade-delete invariants all found to be genuinely enforced at the code level. The most valuable finding is a cluster of drift in the routing-quality domain rule: the PRD states a hard "≤10% segment-overlap" constraint as an unmodified, currently-true v1 guarantee, but `LoopRouteGenerator` treats 10% as a soft preference tier and silently falls back to whatever candidate is available, warning only past a much looser, undocumented 40% ceiling — with the 10–40% band surfaced to no one. A second, already-roadmap-tracked gap is that the v2 "modified" business rule for OSM scenic/low-traffic and cyclist-POI preference — narrated in the PRD's Business Logic Changes section in the present tense — has zero implementation anywhere in the backend (`S-07` is parked). Both gaps sit squarely in what Step 2 classifies as the Core subdomain, meaning the place where the PRD and the code disagree most is also the place the product's actual value proposition lives — which is why Step 5 ranks the overlap/paved fallback logic as the #1 refactor target.
